# Step 8.5 — Administration, and the statements index

**Status:** ✅ built, gate passed · **Depends on:** Step 8 · **Blocks:** nothing

> **Not a roadmap step.** Steps 9 and 10 are dot-matrix slips and cutover. This
> is the four rail entries that have been sitting greyed out since Step 4 —
> Users, Audit log, Settings, Statements — and the reason to do them before
> Step 9 is that three of the four are screens over endpoints that already
> exist and are currently unreachable by anyone who is not holding `curl`.

---

## Goal

**Make the system administrable from inside itself.** Today an account cannot
be turned off, a password cannot be changed, a setting cannot be altered except
through the one switch bolted to the dashboard, and the audit log — the record
the whole of Step 2 was built to produce — has never been looked at through a
browser.

That last one is the real motivation. An append-only log nobody can read is a
log nobody can use. The triggers, the coverage test, the `Change{Before, After}`
plumbing threaded through every mutating route: all of it exists to answer "what
happened, and who did it", and there is no screen that asks.

## Done when

A manager can, without touching a terminal:

- see every account, create one, turn one off, change one's role, and reset a
  forgotten password — and cannot lock the station out of its own management
  while doing so;
- read the audit log, narrowed to one person, one kind of action, one record or
  one week, and open a row to see exactly what changed;
- change any of the eleven settings, see what each one means, and check that
  last night's backup actually got written;

and anyone signed in can find a farmer's statement by name or code, with the
balance they will be read out showing next to them before they click.

---

## What is already there, and must not be rebuilt

Two findings from reading the code before planning. Both shrink the work, and
the second one is load-bearing for a refusal in 8.5.1.

**`withSession` re-reads the user on every request.** `internal/api/auth.go`
looks the account up by id and ends the session if `!user.Active`, with a
comment saying that is what makes deactivation immediate rather than
thirty-days-away. So deactivation needs no session sweeping, and a role change
takes effect on the next request for free, because `user.Role` is re-read on
that same path. A password reset is the one that does *not* ride this: the hash
changes, the session rows do not.

**`routes_test.go` enumerates the route registry** and fails on a mutating route
that has not chosen an audit style. Every endpoint below is audited because it
cannot be registered otherwise — the guarantee stays structural, and this step
adds nothing to the exception list.

**One correction to make on the way past.** `settings.Kind.String()` returns
prose: `"one of a fixed list"`, `"time of day as HH:MM"`. It is written for a
human reading an error message, and the settings screen must not switch a form
control on it. `Kind.Slug()` is added beside it — `string`, `int`, `bool`,
`time_of_day`, `timezone`, `choice` — and the API sends both: `kind` stays the
sentence under the field, `kind_slug` picks the editor.

## Tasks

### 8.5.1 — What an account can be told to do

`internal/auth/user.go`, four functions in the shape the package already uses —
a `Tx` variant, because every one of these is audited and the audit entry must
commit with the change:

- `SetActiveTx(ctx, tx, id, active) (User, error)`
- `SetRoleTx(ctx, tx, id, role) (User, error)`
- `SetPasswordTx(ctx, tx, id, plaintext) error` — validates through the existing
  `ValidatePassword`, hashes through the existing `HashPassword`
- `CountActiveManagersTx(ctx, tx) (int, error)`

and in `session.go`, `DeleteForUserTx(ctx, tx, userID) (int64, error)`, plus a
variant that spares one session id — a manager changing their own password
should not be signed out of the tab they are standing at.

**Three refusals, and where each one lives.**

| Refused | Why |
|---|---|
| Demoting or deactivating the **last active manager** | The station would have no one who can undo it. |
| Deactivating or demoting **yourself** | Same click takes away the screen and the fix, which is the LAN switch's argument. |
| Changing **your own** password without the current one | A manager reset is deliberate; a hijacked session must not be able to lock the owner out. |

The last-manager count runs **inside the transaction, after the write**, and the
transaction's first statement is the `UPDATE`.

> **Built, and this is where the plan was wrong.** It predicted that counting
> *before* the `UPDATE` would lose the last manager. It does not. Inside a
> transaction a count-then-write is a read-then-write, and WAL hands the second
> transaction a snapshot conflict its `UPDATE` cannot recover from — SQLite
> defends that shape for us. Measured over twenty concurrent demotions, it is
> *safe but unusable*: nineteen of twenty writers die on the conflict, which the
> API can only report as a 500.
>
> What actually loses the station its manager is taking the count **outside**
> the transaction — the guard on one connection, the write on another. There is
> no snapshot to conflict with, so both writers pass a guard that was true when
> they read it and false when they acted on it. Held open at a barrier it loses
> both managers on every run.
>
> So the write-first ordering is kept, and for a second reason as well as the
> first: it is the only one of the three that turns the losing writers into a
> sentence a person can read. Ten of twenty commit and ten get `ErrLastManager`.

**Done when:** twenty goroutines demoting the two remaining managers leave
exactly one manager standing, every time, under `-race`, **and at least one of
them is refused by the guard rather than by SQLite** — a survivor nobody turned
away proves nothing; the out-of-transaction guard is shown losing both managers
at a barrier, so the in-transaction one is known to be doing work; a manager
cannot deactivate themselves; a password reset is followed by the old cookie
being refused on the very next request; and a self-change with the wrong current
password is a 401 that does not reveal whether the account exists.

### 8.5.2 — The user routes

Four registrations in `internal/api/api.go`, all through `rt.mutate`:

| Route | Access | Action | Entity |
|---|---|---|---|
| `POST /api/users/{id}/active` | manager | `user.activated` / `user.deactivated` | `user` |
| `POST /api/users/{id}/role` | manager | `user.role.changed` | `user` |
| `POST /api/users/{id}/password` | manager | `user.password.reset` | `user` |
| `POST /api/session/password` | authenticated | `user.password.changed` | `user` |

`Change.Before` and `Change.After` carry `auth.User` values, which is what makes
a leaked hash impossible rather than merely unlikely — the struct has no hash
field, and `handleCreateUser` already says so in a comment. Nothing in this step
weakens that; the password routes report `Before`/`After` as the user record,
never the credential.

The two activation actions are distinct strings rather than one
`user.active.changed` with a boolean in `after_json`, because the audit screen's
action filter is a list of what happened and "somebody turned an account off" is
a different question from "somebody turned one back on".

**Done when:** `TestUserRoutesAreRegisteredWithTheRightAccess` asserts the table;
an encoder is refused on the three manager routes and each refusal is audited;
and the coverage test still passes with no new entry in the self-audited
exception list.

### 8.5.3 — The Users screen

**Change password…** goes in the sidebar's user block, not the topbar — the

the sign-out button have been in the sidebar since Step 4, and a fourth control
belongs beside the three it is a sibling of. It is the only part of this task an

### 8.5.4 — Audit filters

`internal/api/audit.go` gains `user_id`, `action`, `entity`, `from` and `to`,
carried **alongside** the existing `before` cursor rather than replacing it, so
paging stays stable while a filter is on. `idx_audit_at`, `idx_audit_user` and
`idx_audit_entity` already cover three of the four; `action` is low-cardinality
and scans acceptably at this table's size, and is worth an index only when the
log is big enough to prove it needs one.

`GET /api/audit/facets`, manager-only, returns the distinct usernames, actions
and entities **present in the table**. Not a hard-coded list: the action strings
live partly in `internal/audit`'s constants and partly in `rt.mutate` call
sites, and any list written down in a third place drifts from both. What has
happened is exactly what is worth offering to filter by.

> **One gotcha the plan did not see, found while writing the query.** `at` is
> written with `time.RFC3339Nano`, which **drops trailing zeros from the
> fraction**. So the same instant is stored as `…T00:00:00Z` or
> `…T00:00:00.123Z` depending on the clock, and comparing those against a full
> RFC3339 day boundary lexicographically is wrong: `.` sorts before `Z`, so an
> entry a fraction of a second into a filtered day tests as *earlier* than that
> day's own midnight and is dropped. The boundary is therefore truncated to
> whole seconds with no zone suffix, so every stored value beginning with those
> nineteen characters sorts after it. The obvious implementation loses two of
> the first three entries of a day, and the test says so.
>
> **And the LIKE mutation is not the one it looks like.** A dot is *literal* in
> SQL `LIKE`, so `user.created` as a pattern matches only itself and swapping
> `=` for `LIKE` goes unnoticed from that direction. What `LIKE` actually leaks
> is `_` — any single character — and ASCII case-insensitivity. The test is
> driven from the underscore and from an uppercased action, which catches it.

**Done when:** every filter combination returns precisely the subset the
unfiltered query would, checked against a seeded log; `from`/`to` are inclusive
at both ends and interpreted in the station's timezone, matching the `at` column
the same handler already converts for display, **including an entry in the first
instant of the first day**; a bad `user_id` is a 400 naming the parameter; and
paging with a filter on never repeats or skips a row while new entries arrive
mid-scroll.

### 8.5.5 — The Audit log screen

`web/src/pages/AuditPage.vue`. The filter bar, the table, Load older, and a row
that expands to show `before`, `after`, the request id and the IP.

`before_json` and `after_json` stay raw text on the wire — `audit.go` is
explicit that re-encoding them through today's Go structs would quietly rewrite
history — so the screen pretty-prints **for display only** and shows the raw
text if it does not parse. A row the current code cannot make sense of is still
a row that must be readable.

> **Three faults from walking it, and a guard that came out of them.**
>
> The three filter dropdowns rendered as empty boxes. PrimeVue shows nothing at
> all for a `null` model unless a placeholder is set, and "no filter" is exactly
> what `null` means here — so the bar looked broken in its resting state, which
> is the state it is in every time the screen opens.
>
> At 390px each dropdown grew to about 150px tall. The narrow-width rule put
> `flex: 1 1 10rem` on the `Select` as well as on the field around it, and the
> field is a *column* flex container — so the grow applied vertically. Invisible
> at any width where the filter bar does not wrap.
>
> And half the log read in English while the other half printed raw action
> strings, because the wording table had the account actions in it and none of
> the customer, advance, payment or interest ones. The fallback to the raw
> string is deliberate and stays, but it is meant to cover an action a later
> step adds before the list catches up — not to be the normal state.
>
> That last one is now a test rather than a promise.
> `TestEveryAuditActionHasAWordingOnTheScreen` reads `web/src/api/audit.ts` and
> checks it against the route registry, the audit package's constants and
> `customer.ActionImported`; a second test checks the reverse, so a wording for
> an action nothing writes is caught too. It found a real gap immediately: the
> `Change.Action` override added in 8.5.2 meant `user.deactivated` was written
> by a handler and was not on the registry at all. `Route.AlsoWrites` now
> declares it, which puts the registry back to being the complete answer to
> "what can end up in `audit_log`".

**Done when:** walked at 1024px and swept to 390; an entry from every action
currently reachable renders without a blank column and in words rather than in
dotted identifiers, checked by a test rather than by eye; and a log with one
entry, and with none, both read as themselves rather than as a broken table.

### 8.5.6 — Settings and Backups

`web/src/pages/SettingsPage.vue`, manager-only. The eleven settings grouped
Station / Interest / Payments / Numbering / Network / Backup, the editor chosen
by `kind_slug`, `doc` printed under the field as the hint.

Two places the generic screen is not generic enough, and both earn their
exception:

- **`interest.rate_bps`** prints `= 3.00%` beside the box. Basis points are how
  the system stores it and not how anybody thinks, and a manager typing `3`
  meaning three percent is a hundredfold error in the direction nobody checks.
- **`network.lan_access`** renders disabled off-host, with the reason. The
  server refuses that key from anywhere but the host machine and will go on
  refusing it; offering a control that cannot work reads as a fault.

The Backups panel goes on this screen and nowhere else, over the two endpoints
that already exist: the folder's contents with sizes, and Back up now. Its 503
is surfaced as written — the message names the folder, because the cause is
almost always the USB stick not being plugged in.

No server change in this task beyond `Kind.Slug()`.

> **The backups panel found a fault older than this step.** A backup's file name
> is UTC by decision — it has to sort lexicographically in a directory listing
> whatever locale the host is in — and the first version of this panel printed
> the file's *modification time* beside that name. In this timezone that is
> `bokkie-20260918-022238.db` labelled "10:22 AM", eight hours apart, on the one
> screen whose job is to answer "did last night's backup run".
>
> Modification time was the wrong source anyway, and `backup.List` already said
> so in a comment: a file copied off a USB stick and back has a modification
> time recording the copy, not the backup. `backup.TakenAt` reads the instant
> out of the name and the API converts it to station time, so the name and the
> time shown are provably the same instant. The panel says which is which.
>
> **And the same CSS mistake was made twice.** `flex: 1 1 18rem` written for a
> row is a *width*; the moment a narrow-width rule turns that row into a column
> the identical declaration is a **height**, and every setting grew a 288px gap
> between its label and its control. The audit filter bar had it too, with the
> dropdowns 150px tall. Both were invisible at every width where the layout did
> not wrap, which is every width anybody develops at.

**Done when:** every setting in `settings.All` renders an editor — asserted by a
test over the list, not by counting them by eye, so a setting added later cannot
land on the screen as a blank row; every setting and every choice option has
words rather than its key, asserted by a test that reads the TypeScript against
`settings.All` in both directions; a rejected value shows the server's sentence
against the field it belongs to; and the LAN switch on this screen and the one
on the dashboard agree after either is used.

### 8.5.7 — The statements index

`GET /api/statements?as_of=&q=&status=&page=&per_page=` — the customer list's
own query, joined against `ledger.BalancesAt(as_of)`, which is already one
query for every customer. A customer with no ledger entries at all is absent
from that result and renders `0.00`; they are not dropped from the list.

**This route is `Authenticated`, and that departs from the reports.** The four
reports are manager-only because they are portfolio views. An index across every
farmer's balance is arguably one too. It is registered as `Authenticated`
anyway, for two reasons: the person who has to tell a farmer what they owe is
the encoder at the counter, and any single farmer's balance is already one click
from `/customers`. What the index adds is the saving of those clicks, not access
to a figure that was withheld. `nav.ts` has always agreed — Statements is the
one entry under Insight carrying no `manager: true`.

Recorded here because it is the kind of decision that looks arbitrary in six
months. If it turns out an encoder should not see the book ranked, the change is
one argument at the registration and one flag in `nav.ts`.

`web/src/pages/StatementsPage.vue`: the as-at date, the search box, the table,
each row linking to `/customers/:id/statement`. Nothing batch-prints. The
comment in `nav.ts` promising "statements across customers, printed in one run"
is wrong as of this step and gets corrected rather than left to mislead.

**Done when:** the balance on every row equals what that customer's own
statement closes at on the same date — checked over a seeded book, because two
routes computing one figure by different paths is exactly the disagreement Step
6 refused to allow; search behaves as `/customers` does, including a typed `%`;
and a customer who has never borrowed appears with `0.00`.

## Order, and why

**Users, Audit, Settings, Statements.**

Users first because it is the only task here with an irreversible failure mode.
Everything else in this step is a screen over a read, or a write whose worst
outcome is a wrong number that can be set back. Locking the station out of its
own administration cannot be undone from inside the application at all — it is a
sqlite3 shell on the host, at which point the person holding the problem is the
one who least wants to be. A guard is worth finding early.

Statements last because it is the one task that is genuinely new server work
rather than a screen over something built in Step 2, and because nothing in the
step depends on it.

## What this step does not do

- **No bulk statement printing.** Decided against: the section is a way to find
  the right statement, not to produce a stack of them. If the station later
  wants a run, it is a new task against the same index.
- **No account deletion.** Accounts deactivate and never delete, for the reason
  customers do not: the audit log references `user_id`, and a deleted account
  turns every entry it wrote into an orphan.
- **No self-service password reset.** There is no mail on this machine and no
  second factor. A forgotten password is a manager's job, which is what 8.5.1's
  reset route is for, and the last-manager guard is what keeps somebody able to
  do it.
- **No audit export.** The log is readable and filterable; getting it out of the
  building is a question nobody has asked yet, and `bokkie backup` already
  carries the whole table.
