# Step 2.6 — One File From the Internet

**Status:** ⬜ specified, not built · **Depends on:** Step 2.5 · **Amends:** Step
2.5's "updates are manual, from a USB stick"

---

## Goal

Replace *copy a folder off a USB stick and run two files inside it* with
**download one file and double-click it**.

The station is installed and updated from GitHub over HTTPS. The USB folder
survives untouched as the offline fallback — nothing in `bokkie update <folder>`
changes, because the day the internet is down at a buying station in Pintor Gamu
is not a hypothetical.

Three decisions were taken before this was written:

| | Decision |
|---|---|
| **A** | GitHub is the primary channel. USB is the offline fallback, not the default. |
| **B** | The setup `.exe` **is** `bokkie.exe`, renamed. Not a wrapper around it. |
| **C** | A downloaded setup exe verifies **its own bytes** against the signed manifest it fetches from the same release, before it touches the service. |

## Done when

- A person at the station with a fresh Windows 10 machine, a browser and no
  instructions beyond the page gets bokkie installed and answering at
  `http://bokkie.local:8080`, having downloaded **exactly one file**.
- Double-clicking that same file on a machine that already has bokkie offers
  update / repair / shortcut / uninstall. It never silently reinstalls.
- An update applied this way is refused unless `latest.json` is signed by the
  release key and names a SHA-256 matching the setup exe's own bytes.
- Bokkie appears in Add/Remove Programs, and removing it there leaves the data
  folder and the service account in place — the promise `uninstall` already makes.
- A counter PC gets its desktop shortcut from the same file, **without**
  administrator rights and without installing anything.
- The `windows-latest` job has installed, confirmed `/healthz`, and uninstalled
  the exact binary in the release — so the Windows path has been run *somewhere*
  before it is run at the station.
- The download page names the current version and its hash without anyone
  editing the page.

## Deliberately not built

- **A silent/unattended switch.** There is one host machine.
- **Code signing.** See D9 — a certificate is money, and the warning it removes
  is survivable with instructions.
- **The service updating itself.** A person still double-clicks. The download is
  the only part of OTA being added; see *Forward compatibility*.
- **macOS and Linux installers.** The `.command` wrappers stay exactly as they are.

## Decisions

### D1 — The setup exe is bokkie.exe, renamed

`internal/service.Install` is already an installer. It creates the service
account, **copies the running binary to `%ProgramFiles%\Bokkie\bokkie.exe`**
(`placeExecutable`, resolved from the environment so a non-`C:` system drive
works), grants the data directory to the account, registers the service to run
`run --data-dir … --console=false`, opens the firewall for the private and
domain profiles only, starts it, and confirms `/healthz` answers.

Nothing in that list is missing. What is missing is a front door: today
double-clicking the binary prints usage to stderr and exits 2 — a console window
that flashes and vanishes, which is the open item step 2.5 named "the operator's
first inch" and did not close.

So `BokkieSetup.exe` is byte-identical to `bokkie-win-amd64.exe` under a name
that tells the owner what to do with it. A wrapper that embedded the binary
would double the download, add a second artifact to sign, and duplicate a copy
step that `install` already performs correctly.

### D2 — An Explorer launch is detected, not guessed

`GetConsoleProcessList` returning 1 means this process is the only one attached
to its console, which means the console was created for it — Explorer, not
`cmd`. Only then does a no-argument launch run guided setup.

Everywhere else a no-argument launch keeps printing usage and exiting 2, so
scripts, the Makefile and the pre-push hook see no change at all. The service
never reaches this path: it is registered *with* arguments.

### D3 — Elevation is native, and the elevated child is unambiguous

`ShellExecuteW(…, "runas", …)` replaces the `.cmd`'s PowerShell
`Start-Process -Verb RunAs`. The relaunch passes an **explicit argument** rather
than relaunching bare — a bare child would re-run D2's detection, decide it was
double-clicked, and be unable to tell it was already the second attempt. A
cancelled UAC prompt is then reported as a sentence rather than becoming a loop.

The parent exits immediately after spawning and does **not** pause: two windows
waiting for Enter, one of them behind the other, is how a person ends up
believing the install hung.

### D4 — The window stays open, on success and on failure

The `.cmd` files end in `pause` for a reason, and that reason does not disappear
when the batch file does. Every exit from the guided path waits for Enter, with
the failure text saying what to send the developer — the same words
`Install Bokkie.cmd` uses today.

### D5 — The counter PC gets its shortcut from the same file

`Create Bokkie Shortcut.cmd` exists because counter PCs need the Edge `--app=`
shortcut but must not install anything. Folding it in means the guided path, run
on a machine with no bokkie service, offers **both**: install the system here, or
just put a shortcut on this desktop pointing at the host. The second needs no
administrator rights, which is why it must be offered *before* elevation is
requested, not after.

The `.lnk` is written from Go. The host address is asked for when
`bokkie.local` does not resolve, which is the fallback the `.cmd` documents in
its closing message.

### D6 — Add/Remove Programs is one registry key, and its uninstall needs the same care

`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\Bokkie` with
`DisplayName`, `DisplayVersion` from `buildinfo`, `Publisher`,
`InstallLocation`, `DisplayIcon` and an `UninstallString` pointing at the
installed binary.

The trap: Windows runs that string **without a console**, so the uninstall verb
it names must itself detect that it has no window to print into, confirm with a
dialog rather than a prompt, and not vanish silently. Uninstall keeps leaving the
data folder and the service account alone.

### D7 — A downloaded file proves itself; an offline first install says plainly that it could not

The setup exe hashes **its own bytes**, fetches `latest.json` and
`latest.json.sig` from the release it claims to come from, verifies the signature
with the `PublicKey` already compiled in, finds the `windows/amd64` artifact and
compares. Mismatch refuses, in the words `internal/release` already uses.

The asymmetry that matters:

- **Updating** an installed station with a file that cannot be verified — no
  network, or a fetch that fails — is **refused**. A working system is not
  replaced on the strength of a file nobody checked.
- **First install** on a machine with no bokkie on it proceeds, saying in plain
  words that it could not be checked and what to do instead (the USB path, which
  carries its manifest beside it). Refusing here would mean an offline station
  cannot be installed from a stick someone downloaded elsewhere — which is the
  whole fallback.

### D8 — `releases/latest/download/` removes the need for an API call

GitHub serves a stable redirect at
`…/releases/latest/download/<asset>` that always resolves to the newest
non-draft, non-prerelease release. So:

- The page's download button is a plain `<a href>` — no JavaScript needed for the
  thing the owner actually clicks.
- "Check for updates" inside the setup exe is one fixed URL, with no GitHub API
  dependency, no token, and no rate limit to reason about.

JavaScript on the page is used only to *display* the version and SHA-256, and the
page states both are readable from `latest.json` if the script does not run.

### D9 — SmartScreen is documented, not defeated

An unsigned executable downloaded from the internet carries Mark-of-the-Web, and
Windows 10 will show **"Windows protected your PC"**. The way past it is
*More info* → *Run anyway*, which the existing `.cmd` comments already expect.

An OV certificate is roughly $200–400/year and still needs reputation to
accumulate before the warning stops; EV stops it immediately and costs more. For
one station, the warning is cheaper than the certificate — **so the page shows
the exact two clicks, with the SHA-256 beside them** so a suspicious person can
check the file rather than trust the sentence.

Revisit if bokkie is ever handed to a second station.

### D10 — The signing key does not go to GitHub

This is a correction to "let CI build and publish". `make sign` needs the private
release key, and step 2.5 is explicit that the private half never enters this
repository. A repository secret is not the repository, but it is still a copy of
the one key whose loss or theft locks every installed host out of updates
forever.

So the pipeline splits:

| Where | What |
|---|---|
| Your Mac | `make release` — builds, signs. The key never moves. |
| Your Mac | `make publish` — `gh release create` as a **draft**, assets attached. |
| `windows-latest` | On the draft, downloads the real assets, installs, confirms `/healthz`, uninstalls. |
| You | Publish the draft once that check is green. |

`make ci` and the pre-push hook remain the gate. The workflow is a Windows test
rig, not an approval — which keeps the "no hosted CI by design" decision intact
in substance: nothing about whether code is good is decided by GitHub.

**To verify while building:** a draft release fires the `release` event with
action `created` but not `published`. If that proves unreliable, the fallback is
`workflow_dispatch` taking a tag.

### D11 — The page lives in `site/`, not `docs/`

`docs/` holds the plans and the runbook. Pointing GitHub Pages at it would
publish the internal planning record — including this file — as a website.
A separate `site/` directory is deployed by the Pages workflow.

## Gotchas

- **The manifest refuses unknown fields.** `ParseManifest` uses
  `DisallowUnknownFields`, deliberately. Nothing new may be added to
  `latest.json` without the compatibility thought that decision was written to
  force.
- **The Windows artifact's filename appears in four places**: `make build-all`,
  the manifest's `file` field, `pick-binary.sh`, and `Install Bokkie.cmd`'s
  existence check. The manifest is read, so it follows a rename — the two shell
  files are hardcoded and will not.
- **The elevated child gets a new console.** The parent's window closes while the
  child's opens. Looks like a crash if the parent prints something hopeful first.
- **Windows Defender quarantines unsigned, freshly-published executables** more
  eagerly than SmartScreen warns about them. Worth testing the real download on
  the real machine before the owner is standing there.
- **`windows-latest` is Windows Server, not Windows 10.** SCM, `netsh`, and the
  service account path are genuinely exercised. `bokkie.local` mDNS resolution —
  the single most likely support call — is **not**, and no runner will prove it.
- **The runner cannot check the shortcut by clicking it.** Verify by reading the
  `.lnk` back and asserting its target and arguments.
- **Mark-of-the-Web does not follow the install copy**, since the copy is written
  as a new file rather than cloned with its alternate data stream. The installed
  binary is clean; only the download in the Downloads folder is tagged.
- **Neither prerequisite from step 2.5 is done.** `make keygen` with the public
  half pasted into `internal/release/verify.go` and the private half backed up
  off the machine, and a first version tag. Until both, `PublicKey` is empty,
  every update is refused by design, and `make release` refuses to run. **None of
  this step can produce a real download until they are.**

## Forward compatibility

Step 2.5 promised that OTA would later "add a download and change nothing else".
This step is that download, and nothing else — the signature verification, the
backup-and-rollback sequence and the service restart are reused as they stand.

What is still absent from true OTA is the unattended part: the *service*
replacing itself with no one present. The rename-aside file dance that needs is
already written and tested in `internal/service/replace.go`; what is left is the
process handoff, and it stays where step 2.5 put it.

the two things step 2.5 left for a human are done: `make keygen` with the public
half pasted into `internal/release/verify.go` and the private half backed up off

### Deviations from the plan, and why

**`BokkieSetup.exe` is a copy, not a rename.** The manifest keys artifacts by
platform and `Artifact.Verify` compares bytes, so the copy verifies against the
same signed entry under either name. The manifest, `pick-binary.sh` and
`Install Bokkie.cmd` therefore need no change, which deletes the
four-places-to-forget gotcha this document warned about rather than managing it.

**`windows.GetConsoleProcessList` does not exist in x/sys v0.48.0.** The
kernel32 call is declared directly rather than moving the module for one call.
This is the one piece of the step with no test and no type-check that can fail —
if it returns 0 on a real console, a double-click shows usage instead of the
window. Only the runner can catch it.

**The plan's `needsAdmin` read the flag back out of a menu**, which can only
answer for actions that menu happens to contain — update never appears on a
machine running the same version. One map is now the source, and `menuFor` reads
it.

**An install that is not answering has no version to compare against.** The
first draft offered to "update from an installed copy that is not answering" to
`dev`. It is a repair.

### Still unverified

- **Everything Windows-specific.** No line of it has run. The runner is the
  first execution and the station is the first real one.
- **`bokkie.local` on a Windows 10 counter PC** — the most likely support call,
  and no runner will ever show it. This is Step 1's outstanding drill, and this
  step is the first that has the hardware to run it.
- **SmartScreen and Defender.** Whether the warning is the one the page
  describes, and whether Defender quarantines a freshly published unsigned
  executable, are both findable only on the real machine with a real download.

### What the review found

A fresh review of the whole branch found two faults that would each have been
discovered by the owner rather than by anyone here.

**The desktop shortcut hung on every machine.** The address prompt read its
input to EOF, and a console's stdin does not reach EOF when somebody presses
Enter — on the first item of the first menu a counter PC is offered. There was
no test for it, and any test written in the obvious way would have passed,
because a string reader ends.

**Install and repair printed the refusal and installed anyway.** The gate
returned a decision and the call site dropped it, so a file whose bytes did not
match the release could reach the service through Repair — the default choice on
an up-to-date station — after the screen had said "Nothing has been changed".
The decision function had a test; the wiring did not.

Both are fixed, with tests that fail against the old code. The review also
corrected the uninstall path (Windows runs an `UninstallString` unelevated, so
removing Bokkie from Add/Remove Programs could never have succeeded), the
failure message that promised an untouched machine after the service had already
been deregistered, and the runner — which passed arguments at every step and so
never once called the hand-declared `GetConsoleProcessList` it was added to
exercise.
