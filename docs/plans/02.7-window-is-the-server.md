# Step 2.7 — The Window Is the Server

**Status:** ⬜ specified, not built · **Depends on:** Step 2.6 · **Reverses:** Step 1's service model

---

## Goal

Bokkie runs while its window is open and stops when the window closes. There is
no service, no administrator prompt, and nothing installed.

Plus: when `bokkie.local` is already claimed by another machine, the window says
so and offers a different name rather than leaving the counter PCs pointed at
somebody else's computer.

## The decision this reverses, and what it costs

Step 1 chose a system service, and `internal/service`'s own comment says why:

> A service that only runs while a user is logged in is a common and painful
> mistake, and it is not discovered until the morning the station reboots.

That objection was put to the owner of this decision and the decision stands.
It is recorded here so that the consequences are known rather than discovered:

| | Consequence |
|---|---|
| **1** | **After a power cut the station is down** until a person logs in and opens the window. Isabela's supply is not reliable; this will happen. |
| **2** | **A closed window is a closed station.** Anyone who tidies their taskbar takes the counter PCs offline. |
| **3** | **The nightly backup only runs while the window is open.** `backup.Scheduler` runs in-process. A station shut at night is a station that does not back up — and backups are the whole of this system's recovery story. |
| **4** | **Step 1's gate becomes unreachable.** "Reboot the host and confirm the app still answers with nobody logged in" cannot pass by construction. |
| **5** | **Windows Update reboots the host without asking.** The station comes back with the window shut. |

Mitigations are in the design below. None of them removes consequence 1.

## Decisions

### D1 — The window is the process, and nothing else may start it

Double-clicking the exe opens a window that serves until it is closed. Closing
it — the X, Ctrl+C, a logoff — drains in-flight requests, withdraws the LAN
name, closes the database and releases the port.

**This is a hard requirement, not a default.** A person opening the window is
the only way the station is ever served. In particular bokkie must never
install, and must actively refuse to leave behind:

- a Windows service of any kind, including a manual-start one;
- a `Run` or `RunOnce` registry key;
- a Startup-folder shortcut;
- a scheduled task, including "at logon" and "at startup";
- anything restarted by Windows' own recovery settings.

A reboot, a power cut and a Windows Update restart all leave the station **not
serving** until somebody opens the window. That is the specified behaviour. A
test asserts each of the five above is absent after a run, because this is the
kind of requirement that erodes one convenience at a time.

### D2 — Nothing is installed, so nothing needs administrator rights

No service, no account, no `netsh` firewall rule, no Add/Remove Programs entry.
Windows raises its own "allow access" prompt the first time the port is bound,
which is one click by whoever is already standing there.

### D3 — The data folder moves to where a normal user can write

`C:\ProgramData\Bokkie` was chosen because a service account had to read it. With
no service account the first user to run bokkie creates it and owns it, and a
second Windows user on the same machine may then be unable to open the database
at all.

The data folder becomes `%LOCALAPPDATA%\Bokkie` — per user, always writable, no
prompt. **An existing `C:\ProgramData\Bokkie` is adopted rather than ignored**:
if one is found and the new location is empty, it is used in place, so an
upgrade from 2.6 does not silently start an empty ledger. A station that cannot
read its own ledger is the worst failure this system has, and it must not be
possible to reach it by double-clicking a newer exe.

### D4 — Backups get a visible pulse, because they no longer have a night

Consequence 3 is the one that costs money. The window therefore:

- takes a backup on startup, so every session has one;
- takes a backup on clean shutdown, so closing the window is itself a save;
- shows the time of the last backup on screen, so "when did this last back up"
  is answered by looking rather than by asking.

The nightly schedule stays for the stations that do leave it open.

### D5 — A contested name is offered a new one

When the name already answers from another machine, the window says which
address it resolves to and which this computer has, then offers:

1. Use this computer's address instead — printed, and used for the counter-PC
   shortcuts.
2. Choose a different name. Whatever is typed becomes `mdns.hostname` in the
   settings file; `tls` gives `tls.local`. The shortcut path uses it too.

Picking a name that is also taken asks again rather than publishing it.

### D6 — Update becomes replacing a file

With no service to stop, `bokkie update` is: verify the signature, back up the
database, and swap the exe. The rename-aside sequence and rollback in
`internal/service/replace.go` are kept and reused; the stop/start either side of
them goes. `internal/update` loses its service dependency and keeps its backup.

### D7 — `install` and `uninstall` stay, and stop being the Windows story

They remain for macOS and Linux hosts, where launchd and systemd are the normal
way to run something and no window is involved. On Windows the setup menu stops
offering them. The code is not deleted — deleting the one proven path to an
unattended station, in the same change that removes unattended operation, would
leave nothing to go back to.

### D8 — Upgrading removes the service 2.6 installed

A station already running v0.0.1 or v0.0.2 has a Windows service registered and
set to start automatically. Shipping this change without removing it would mean
the one machine being upgraded is the one machine that still auto-starts —
violating D1 on the only host that exists.

So the first run of a 2.7 build, on Windows, looks for the `bokkie` service and
removes it: stop, deregister, drop the firewall rule and the Add/Remove Programs
entry. It says what it did. It needs administrator rights to do it, so it asks
once, and if refused it says plainly that the old service is still installed and
will still start on its own.

### D9 — The UI is the app's own window, not a console

The commands get a screen. A console that prints a numbered menu is a CLI with
extra steps, and the people using this are counter staff.

The exe opens the app in a browser window in application mode — no address bar,
no tabs — which is what the counter PCs already use and what `Create Bokkie
Shortcut.cmd` has always made. That window is the station's switch: while it is
open the station is served, and closing it stops everything.

This needs no new dependency and no GUI toolkit, which matters in a project that
is `CGO_ENABLED=0` by decision. The screens are Vue, like every other screen in
the system, and the status they show comes from the API the app already has.

Three screens are new:

- **Status** — is it serving, at which address, the last backup, and a Stop
  button. This is what the window opens on.
- **Check** — `doctor`'s report, rendered. The same checks, the same words, in a
  list a person can read without a terminal.
- **Name** — the LAN name, and the contested-name flow from D5.

If no browser can be found the exe falls back to the console menu, which still
exists and is still the thing driving it.

## Done when

- Double-clicking the exe serves the app, and closing the window stops it: the
  port is free and the name is withdrawn within seconds.
- **After a reboot with nobody having opened the window, nothing is serving** —
  checked on the real machine, and asserted in CI against the five auto-start
  mechanisms in D1.
- A station upgraded from 2.6 has its old service removed, and says so.
- The window opens on a screen, not a numbered console menu.
- A second machine claiming the name is reported, and a name typed into the
  window is advertised in its place.
- A station upgraded from 2.6 opens its existing ledger, not an empty one.
- The window shows when the last backup was taken.
- `bokkie doctor` still explains a port clash, a contested name, and a stopped
  server.

## Deliberately not built

- **Auto-start at login.** Explicitly forbidden by D1, not merely skipped. It
  would be most of the service back under a name that hides it. If unattended
  operation is ever wanted again, step 1's service is still in the code and
  still works — bringing it back is a decision, not an accident.
- **A tray icon.** The window is the switch; a second switch invites a station
  that is running with no window to close.
