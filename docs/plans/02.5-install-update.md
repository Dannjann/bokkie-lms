# Step 2.5 — Install Location, Updates, and the Operator's First Inch

**Status:** ⬜ not started · **Depends on:** Step 2 · **Blocks:** every release after the first

---

## Goal

Step 2 made the system recoverable. This step makes it **replaceable** — the
binary on the host can be swapped for a newer one without a support call, and
without a bad release becoming a data-loss event.

Updates are **manual, from a USB stick**. OTA is deliberately not built here.
But the shape below is the OTA shape with the download removed, because the
expensive half of OTA is not the HTTPS call — it is signature verification, the
backup-and-rollback sequence, and restarting a service into a new binary on
three platforms. Those are built now, exercised by hand for a year, and reused
verbatim when OTA arrives. See **Forward compatibility** at the end for the
contract that keeps that promise honest.

The secondary goal is the first inch of the install. `bokkie install` does
careful work, but it is a CLI verb behind a terminal and an admin prompt, and
the architecture doc promises "a system a non-technical operator can start by
double-clicking one file." Today, double-clicking the binary prints usage to
stderr and exits 2 — a console window that flashes and vanishes.

## Done when

- The service runs from a fixed path that does not depend on where the binary
  was sitting when someone installed it.
- `bokkie update <file>` takes a verified backup, swaps, restarts, confirms
  `/healthz`, and **puts the old binary back by itself** when the new one does
  not come up.
- A release that has not been signed is refused.
- Nothing in the runbook asks the owner to edit a YAML file.

---

## Where this stands today

Worth stating plainly, because most of the risk is in what is *absent* rather
than in what is wrong:

| | |
|---|---|
| Install | One command, does the right things: dedicated account, reachability check, quarantine clear, firewall, start, `/healthz` verify |
| Install location | **Wherever the binary sat** — `resolveExecutable()` registers `os.Executable()` and the service manager keeps that path forever |
| Update | **Does not exist** — no verb, no packaging, no version check |
| Migrations | ✅ embedded, applied on boot, and `db.Migrate` refuses a *newer* schema, so an old binary fails closed |
| Pre-update backup | ✗ nothing forces one |
| Rollback | ✗ old binary + new schema refuses to start, correctly — but that is only recoverable if a backup was taken first |
| Versions | ✗ **no git tags exist.** `git describe` yields `dev`, so "is this newer" has nothing to compare |
| Double-click | ✗ usage to stderr, exit 2 |

## Tasks

### 2.5.1 — A canonical install location ⭐ do this first

`install` copies itself to a fixed path and registers **that**, rather than the
path it happened to be run from.

| Host | Path |
|---|---|
| Windows | `C:\Program Files\Bokkie\bokkie.exe` |
| macOS / Linux | `/usr/local/bin/bokkie` |

Re-running `install` on a machine that already has it is an **upgrade of the
registered path, not a second service**.

This is the prerequisite for everything else in the step: an update cannot swap
a binary whose location nobody can name. It also retires the
`checkExecutableReachable` failure class by construction — these paths are
root-owned and world-readable, so the `_bokkie` account can always reach them.
Keep the check anyway; a guard that now always passes costs nothing and catches
the day someone passes `--data-dir` somewhere strange.

**Done when:** installing from `~/Downloads` leaves a service pointing at the
canonical path, and deleting the downloaded copy does not stop it starting after
a reboot.

### 2.5.2 — Signed releases, starting with the first one

An ed25519 public key compiled into the binary; the private key on the
developer's machine and **never in the repo**. `make release` emits a `.sig`
beside each binary plus a `latest.json` manifest (version, platform, size,
sha256, signature, notes).

Real semver tags start here. There are none today, which means version
comparison is undefined — decide the rule now: a `dev` build never installs over
a tagged one without an explicit `-force`.

**Why this belongs in the USB step rather than the OTA step.** The binary doing
the verifying must already carry the key. Ship v1.0 without one and v1.0 → v1.1
cannot be verified — so the first OTA update, the one most worth verifying,
would be the one that cannot be. It also gives the operator a single consistent
behaviour instead of "sometimes it checks."

A checksum alone is not a substitute. It travels in the same folder, on the same
stick, down the same wire as the binary; anything that can alter one alters
both. The signature is what lets an untrusted release host — or a USB stick that
spent a week in a drawer — carry a binary that runs as the account owning the
ledger.

**Done when:** `bokkie update` refuses an unsigned file, refuses a file whose
signature does not match, and accepts a good one.

### 2.5.3 — `bokkie update`, split into acquire and apply

Two halves, deliberately separated:

```go
// Source produces a candidate release. fileSource today; httpSource later.
type Source interface {
    Fetch(ctx context.Context) (Release, error)
}
```

**Acquire** is a local path today. **Apply** is everything that matters, and is
identical whichever way the file arrived:

1. Verify the signature. Stop if it fails.
2. Verify the version is genuinely **newer**. Never sideways, never down.
3. **Take a verified backup** — reuse `backup.Run`; refuse to proceed if it
   fails. This is mandatory, not advisory: `db.Migrate`'s refusal to run against
   a newer schema is what makes a bad release safe, and it is only *recoverable*
   if there is a backup from immediately before the swap.
4. Stage the new binary beside the current one.
5. Hand off to the restart helper (2.5.4).
6. Poll `/healthz` — `service.verifyRunning` already does this; install is just
   its only caller today.
7. On failure, restore the previous binary and restart.

The manifest format is settled here, once, and parsed by the same code whether
it came from a stick or a URL.

**Done when:** a USB update works end to end on macOS, and a deliberately broken
new binary rolls itself back with the service coming up on the old version.

---

### 2.5.4 — Restarting a service into a new binary

The platform-specific part, and the reason this step exists now rather than
later — it is the piece nobody should be writing for the first time on the
evening a fix is urgent.

- **Windows** locks a running executable against overwriting, but *permits
  renaming it*. Rename the running exe aside, put the new one in place, restart
  through SCM. A naive copy simply fails.
- **launchd and systemd** keep executing the old inode until the job restarts,
  so replacing the file changes nothing until a restart is asked for.
- The running process cannot supervise its own replacement, so a small detached
  `bokkie apply-update` helper waits for the parent to exit, completes the swap,
  and restarts the service.

**Done when:** a swap and restart completes with nobody logged in, and
`/healthz` reports the new version.

### 2.5.5 — Audit trail and what the operator sees

- `system.update.applied`, `.failed`, `.rolled_back` in `audit_log`, each
  carrying the from- and to-version and the backup taken beforehand.
- A convention for CLI-initiated actions: `UserID 0` with a reserved username,
  since nobody is logged in at a console. `bokkie backup` writes no audit row
  today either — give both the same treatment while the convention is being
  decided.
- The home page already shows version, commit, uptime and database status. Add
  "updated on ⟨date⟩" so the answer to "which build is on that machine?" is on
  the screen the operator is already looking at.

**Done when:** an update leaves one row naming both versions, readable by a
manager in the app.

### 2.5.6 — The first inch

- **Double-clickable wrappers** beside the binary: a self-elevating `.cmd` on
  Windows (`Install Bokkie.cmd`, `Update Bokkie.cmd`), a `.command` on macOS.
  One double-click, one admin prompt, everything after that verified by the
  program.
- **SmartScreen, documented.** An unsigned binary off a USB stick produces
  "Windows protected your PC", and nothing currently prepares anyone for
  *More info → Run anyway*. It goes in the install sheet, not in a README.
- **A shortcut script for counter PCs** that creates the
  `msedge --app=http://bokkie.local:8080` desktop shortcut the architecture doc
  describes and nothing currently produces.
- **`bokkie backup -set-folder <path>`.** The backup folder correctly lives in
  `config.yaml` rather than in settings — it is a path on *this* machine and
  would be wrong the moment the database is restored onto another host. But the
  runbook currently walks a non-technical owner through hand-editing YAML and
  restarting a service to point backups at a USB stick. A command that edits the
  file keeps the reasoning and removes the text editor.

**Done when:** an install and an update are each one double-click plus one admin
prompt, and the runbook contains no YAML.

## Gotchas

- **No tags exist yet.** Every version comparison in 2.5.3 is undefined until
  2.5.2 introduces real ones. Tag before writing the comparison, not after.
- **Backup-before-swap is load-bearing, not politeness.** The forward-only
  migration guard is what makes a bad release safe; the backup is what makes it
  *recoverable*.
- **A self-replacing binary running as a privileged service account is a real
  attack surface.** Verify before writing anything into place, and refuse to
  stage into a world-writable directory.
- **Do not update while a backup is running**, or the update's own backup will
  contend with the nightly one. Take the lock.
- **The station will be on Windows, unverified.** SCM behaviour, the rename
  trick, and the firewall rule are all written blind — this step inherits Step
  1's caveat and must not be declared done on macOS evidence alone.

## Forward compatibility — the contract with OTA

When OTA is built it **adds**: an `httpSource`, a daily check that notifies and
never auto-installs, a manager-facing "Install update" button, an on/off
setting, and a visible "last checked" so an offline host is discoverable rather
than silent.

It **must not have to change**: the canonical install path, the manifest format,
the signature scheme, the apply sequence, the restart helper, or the audit
action names. If a later OTA step finds itself editing any of those, this step
got something wrong and the fix belongs here retroactively.

One thing OTA *will* require that is deliberately not done now: an amendment to
`00-architecture.md`, which currently states the server never makes an outbound
connection. That sentence is true today and should stay true until the release
that makes it false — at which point it becomes "exactly one kind of outbound
connection, carrying the running version and platform and no station data."

## Risks

| Risk | Mitigation |
|---|---|
| Update leaves the host with no working binary | Old binary kept beside the new one; automatic rollback; `/healthz` is the gate |
| A bad release reaches the station | Manual USB means a human decides; signature means only your releases install |
| Windows rename/restart dance fails in the field | Exercised on real Windows before this step is called done |
| Operator updates without a backup | Impossible — the update takes one itself and refuses to continue without it |
| Signing key lost | Key backed up off-machine before the first signed release; losing it means no host can accept any future update |
