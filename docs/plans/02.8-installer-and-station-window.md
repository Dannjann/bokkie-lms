# Step 2.8 — A Real Installer, and a Window of Its Own

**Status:** 🟡 built, not yet run on the station · **Depends on:** Step 2.7 · **Reverses:** 2.7's D2 and D9

---

## Why

Three things were asked for after 2.7 reached the station:

1. **"Hosting still doesn't work — it says connection refused."**
2. A fully implemented, step-by-step installer, not a console menu.
3. After installing, an exe that opens a native Windows window showing the
   station's status, with a button that opens the site in a browser, and
   closing it stops the station.

## The connection refused, and why the window fixes it

"Refused" from the station's own address means nothing is listening. The
server started (the window opened, so `Start` had returned) and then stopped.

2.7 made the station's lifetime the lifetime of a **browser process**: it
started Edge with `--app` and `--user-data-dir`, waited on that process, and
stopped the station when it exited. Whether that process lives as long as its
window is the item 2.7 listed as *still unverified*, and it is not something
this program controls — Edge can hand the window to another process and let
the one it was started as exit. When that happens the station shuts down a
second after starting, and the window the person is looking at says *refused
to connect*.

Not proven on the machine (the logs would show `the window was closed;
stopping` within a second or two of `http server listening`), but it is the
only path in the code that matches the symptom, and 2.8 removes it rather than
patching it: the switch is now a window this process creates and owns, so
nothing outside Bokkie can end the station.

The window also checks `http://127.0.0.1:<port>/healthz` every three seconds
and shows red **Bokkie is not answering** when the port is bound but refusing,
so if the cause turns out to be something else it is shown, not hidden behind a
green light.

## Decisions

### D1 (2.7) still holds

Nothing starts Bokkie without a person. The installer writes no service, no
Run/RunOnce key, no Startup shortcut, no scheduled task, and `verify-windows`
still checks for all five — now after a real install as well as after a serve.

### D2 (2.7) is reversed — Bokkie is installed

`BokkieSetup.exe` is an NSIS Modern UI wizard (`installer/windows/bokkie.nsi`,
built by `make installer`; `makensis` runs on macOS). Steps: Welcome → Choose
components → Install location → Install → Finish.

- **Station computer:** `C:\Program Files\Bokkie\bokkie.exe`, a Start menu
  entry, an optional desktop shortcut, an Add/Remove Programs entry with an
  uninstaller, and an inbound firewall rule for the *program* on private and
  domain networks (never public).
- **Counter PC:** only an Edge `--app` desktop shortcut to the address typed on
  a wizard page. The two are mutually exclusive in the component list, so a
  counter PC cannot become a second station with its own empty ledger by a
  stray tick.

It needs administrator rights, once, which is the price of the firewall rule
and of Program Files. The program itself still runs `asInvoker`.

The data folder does not move: `%LOCALAPPDATA%\Bokkie`, or an adopted
`C:\ProgramData\Bokkie` (2.7 D3). Uninstalling leaves it alone.

Upgrading from 2.6 is handled by the installer (`bokkie installer-hook
prepare`): the old service is stopped and removed *before* the exe is
replaced, since a running service holds it open. `installer-hook finish` grants
BUILTIN\Users modify on an adopted `C:\ProgramData\Bokkie`, so the person who
opens Bokkie each morning need not be the one who approved the prompt.

### D9 (2.7) is reversed — the window is native

A plain Win32 window, written against `user32`/`gdi32` through syscalls in
`internal/winsetup/window_windows.go`. No toolkit and no cgo — the project's
`CGO_ENABLED=0` stands. The words it shows are computed by
`winsetup.DescribeStation`, which is pure and tested on macOS.

It shows: running / not answering / could not start, this computer's address,
the LAN name and IP address for the counter PCs, the last backup, the records
folder, the version. Buttons: **Open Bokkie in browser** (the default browser,
`http://127.0.0.1:<port>/`), **Run a check** (doctor, in a copyable window),
**Stop Bokkie**.

Closing it — X, Alt+F4, Stop, the web screen's Stop, logoff or shutdown — runs
the same `app.Stop` as before: drain, backup, close the database.

Opening it twice focuses the first window.

The icon and an application manifest (Common Controls 6, DPI awareness) are
embedded from `cmd/bokkie/rsrc_windows_amd64.syso`, regenerated by
`make winres`.

`bokkie.exe` stays a console-subsystem program so `doctor`, `update` and the
CI steps keep their output. When Windows made the console for it — a shortcut
or a double-click — it detaches from it at once, and the shortcuts start it
minimised so it is never seen.

`serve` on Windows opens this window; `serve --no-window` is unchanged. The
browser-as-switch code stays for macOS and Linux. `bokkie setup` (the console
menu) still exists but is no longer what a double-click opens.

## Still unverified

No Windows machine is available here. `go vet` for windows passes and
`makensis` builds the installer; nothing has been *run* on Windows yet.

- The window on a real desktop: layout at 100% and 125% scaling, Tab order,
  the colours, the console never flashing.
- The installer end to end, including an upgrade over a 2.6 station with the
  service running. `verify-windows` now runs the installer silently and
  checks what it leaves; the wizard's pages themselves need a person.
- That the "connection refused" is gone on the station.
